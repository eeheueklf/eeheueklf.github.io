## 렌더링이란

Q. 질문 하나 해도 될까?

> `물론이지. 어떤게 궁금해?`

Q. 렌더링은 언제 일어나?

> `React 컴포넌트는 최초에 렌더링이 일어나고, 상태나 props 등의 변화에 따라 다시 렌더링 돼.`

Q. 잠깐, 다시 렌더링된다는게 정확히 무슨 뜻이야? 화면의 DOM을 매번 새로 만드는 건가?

> `아니, 렌더링과 DOM 업데이트는 다른 단계야.`  
> `렌더링은 컴포넌트 함수를 호출해서 이번에 그려질 UI 모양을 계산하는 과정이야. 이 결과는 아직 화면이 아니라 메모리 상의 결과물이지.`  
> `그 다음 React가 이전 결과와 비교해서 실제로 달라진 부분만 DOM에 반영해. 이걸 커밋이라고 해.`  
> `즉, 렌더링이 매번 일어난다고 해서 DOM이 매번 새로 만들어지는 건 아니야.`  

Q. 그러니까 상태가 바뀔때 새로운 UI를 계산하는게 렌더링이라는거지? 그런데 React는 상태가 바뀐걸 어떻게 알지?

> `그게 바로 useState야. 렌더링 사이에서도 값을 유지하며, 값이 바뀔 때 리렌더링을 요청해.`

Q. 그럼 `useState` 안쓰고 그냥 일반 변수에 값을 저장하면 안되는건가?

> `물론 일반 변수에 값을 저장할 수도 있어. 하지만 값의 변화를 반영할 수는 없겠지.`

## 상태를 어디에 둘까

Q. 그런데 컴포넌트가 많아지면 상태도 많아질텐데, 상태는 최상위 컴포넌트에 두면 되는건가?

> `가능하면 상태를 필요로 하는 컴포넌트들의 가장 가까운 공통 부모에 두는 것이 좋아.`

```
App
├── Header
├── Product
│   └── Modal    ← Product와 Modal만 이 상태를 쓴다면, Product에 둔다
└── Footer
```

*상태를 너무 위에 두면, 관련 없는 컴포넌트까지 리렌더링된다.*

Q. 그런데 여러 컴포넌트가 공유하는 상태가 많아지면 상태를 계속 위로 올려야 하잖아. 그러면 컴포넌트 구조가 복잡해지지 않나?

> `맞아. 상태가 실제로 필요한 컴포넌트까지 여러 단계의 props를 거쳐 전달해야하는 경우가 생기지`  
> `그렇게 컴포넌트 구조가 복잡해지고, 서로 멀리 떨어진 많은 컴포넌트가 같은 상태를 사용한다면 그때 Context나 Zustand 같은 전역 상태 관리 방법을 고려할 수 있어.`

*한 컴포넌트에서만 사용한다면 그 컴포넌트에 두고, 가까운 몇 개의 컴포넌트가 공유한다면 공통 부모로 올리고, 애플리케이션의 여러 곳에서 광범위하게 공유해야 한다면 전역 상태를 고려한다.*

## Client State와 Server State

Q. 그런데 API에서 가져온 데이터도 여러 컴포넌트에서 사용할 수 있잖아. 이것도 전역 상태로 관리하면 되는 건가?

> `여기서 Client State와 Server State를 구분해야 해.`  
> `모달, 선택된 탭처럼 현재 화면에서 관리하는 값은 Client State야.`  
> `반대로 상품 목록, 게시글처럼 서버에 원본이 있는 데이터는 Server State라고 볼 수 있어.`  

Q. `Server State`는 직접 fetch해서 `useState`에 넣어 관리하면 돼?
> `물론 가능해. 하지만 직접 관리하려면 로딩, 에러, 캐시, 재요청, 데이터 동기화까지 신경 써야 해.`  
> `작은 프로젝트라면 직접 관리해도 되지만, 규모가 커지면 이런 로직이 복잡해질 수 있어.`  
> `React Query는 이런 Server State를 쉽게 관리할 수 있도록 도와주는 도구야.`  

Q. 그러면 로그인 상태는 어떻게 봐야 하지? 서버와 관련된 정보잖아.
> `로그인 상태와 사용자 데이터를 구분해서 봐야 해.`  
> `서버에서 가져온 현재 사용자 정보는 Server State로 볼 수 있지만, 토큰이나 세션 같은 인증 정보 자체는 인증 시스템의 영역이야.`

## 렌더링 최적화

Q. 지금까지 상태를 어디에 둘지, 어떤 상태를 어떻게 관리할지 정했는데. 그런데 상태가 변경될 때마다 관련 컴포넌트가 다시 렌더링된다면 성능 문제가 생길 수도 있지 않나?
> `그럴 수 있어. 그래서 렌더링이 불필요하게 발생하거나, 렌더링 과정에서 비용이 큰 작업이 반복되는 경우를 살펴볼 필요가 있어.`

Q. 그런데 렌더링은 무조건 줄이는 게 좋은 건가?
> `아니, 렌더링을 없애는 것이 목표는 아니야.`  
> `렌더링 자체는 정상적인 과정이고, 정말 불필요하거나 비용이 큰 작업만 줄이는 것이 진정한 최적화야.`

Q. 그런데 실제로 불필요한 렌더링이 발생하고 있다면 어떻게 줄여?

> `먼저 상태의 위치를 확인해야 해.`  
> `상태를 사용하는 범위보다 너무 위에 있다면 상태를 더 가까운 곳으로 옮기는 것부터 생각해야 하지.`  
> `그래도 렌더링 비용이 크다면 그때 memo, useMemo, useCallback 같은 최적화 방법을 고려할 수 있어.`

Q. 그럼 `memo`, `useMemo`, `useCallback`을 많이 사용할수록 좋은 거야?

> `그것도 아니야.`
> `최적화에는 비용이 있기 때문에 실제 문제가 있는 곳에 사용하는 게 중요해.`
> `결국 순서는 이래.`

```
상태를 적절한 위치에 배치한다
        ↓
불필요하게 넓은 범위가 렌더링되는지 확인한다
        ↓
실제 성능 문제를 측정한다
        ↓
필요한 부분만 최적화한다
```
